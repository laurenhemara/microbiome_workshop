From raw sequencing data to ASVs

Overview

Today’s tutorial follows the dada2 pipeline tutorial, where we’ll use the Divisive Amplicon Denoising Algorithm (DADA) to correct amplicon errors and assign taxonomy to amplicon sequence variants (ASVs).

Our starting point is a set of Illumina-sequenced, paired-end fastq files that have been split (or “demultiplexed”) by sample and from which the barcodes have been removed.

From this ‘raw’ microbiome sequencing data, the end products will be:

  • An amplicon sequence variant (ASV) count table which records the numbers of times each exact amplicon sequence variant was observed in each sample.

  • A taxonomy table which records the taxonomic assignments for each ASV.

We will then import the ASV count table, taxonomy table, and sample metadata into a phyloseq object for analysis.

Learning objectives

By the end of today’s session, you should be able to:

  • Understand what an amplicon sequencing variant is & why we need to control for sequencing errors

  • Understand how to apply the DADA2 pipeline steps to your own datasets

Make a folder with an intuitive name, like ‘MicrobiomeAnalysisWorkshop’, to serve as your working directory. Make sure that this is where all of the data files are saved.

You can do this by pasting the path to your folder into the code below, or from the menu: Session > Set Working Directory > Choose Directory… (CTRL + SHIFT + H).

Processing your sequencing reads

Assessing the quality of your .fastq reads

The FASTQ format stores experimental sequence measurements produced by a sequencing instrument. It can be thought of as FASTA, where every base has an associated quality score (hence FASTQ).

A typical single FASTQ read will have four sections:

  1. A header (@) followed by an ID.
  2. The nucleotide sequence.
  3. A header (+) followed by an ID.
  4. The last line encodes the quality scores for the sequences in section 2 (and should be the exact same length).

Below is an example of a high quality FASTQ read. Here, the header line includes a read ID and the length of the sequence.

@SRR1553607.1 1 length=202 
GTTAGCGTTGTTGATCGCGACGCAACAACTGGTAAAGAATCTGGAAGAAGGATATCAGTTCAAACGCTCAAG
+SRR1553607.1 1 length=202
BB@FFFFFHHHHHJJJJJJJJJJJJJJJJJJJGHIJJJJJJJJJHHHHHFFFFFEEEEEEEEEDDDDDDDDD

And here a low quality FASTQ read:

@SEQ_ID
GATTTGGGGTTCAAAGCAGTATCGATCAAATAGTAAATCCATTTGTTCAACTCACAGTTT
+SEQ_ID
!''*((((***+))%%%++)(%%%%).1***-+*''))**55CCF>>>>>>CCCCCCC65

Typically, when qualities look like “swearing” in a comic book (!@#$%^&*), it means that the data is low quality.

We can use fastQC to check the quality of our sequencing reads before we proceed with analysis. You can either run fastQC as an application on your computer, or as a tool in the command line. This tool will generate a report that lets us assess the quality of our sequencing data.

FastQC has a really well documented manual page with detailed explanations about every plot in the report. Examples of good and bad fastQC reports can also be found on the project website.

Importing your .fastq files

First we’ll define the path object so it points to the folder containing only the raw sequence read files. Then, we’ll read in the names of the fastq files & perform some string manipulation to get lists of the forward and reverse fastq files in matched order.

#assign path to sequencing .fastq files
path <- "/Users/myname/folder1/subfolder2/MicrobiomeAnalysisWorkshop/fastq"

#check which files are in this directory path
list.files(path)

#read in the names of the fastq files
fnFs <- sort(list.files(path, pattern="_R1_001.fastq.gz", full.names = TRUE))
fnRs <- sort(list.files(path, pattern="_R2_001.fastq.gz", full.names = TRUE))

#extract sample names, assuming filenames have format: SAMPLENAME_XXX.fastq.gz
sample.names <- sapply(strsplit(basename(fnFs), "_"), `[`, 1)

#check the sample names
sample.names
Considerations for your own data

The string manipulations (which assume a SAMPLENAME_R1_001.fastq.gz file naming convention) may have to be modified if your filename format is different.

Adjustments for iSeq100 (2 x 150 bp) sequences

Read in the forward reads only. For all future steps, only run code for the forward reads.

The iSeq100 processes 2 x 150 base pair (bp) sequences - 1 forward and 1 reverse read, totaling 300 bp. The target sequence length for the 16S rRNA V4 region can vary from 250-350 bp. This means that the forward and reverse reads from the iSeq100 are too short to overlap for V4 sequences longer than 250 bp.

The DADA2 filtering and merging steps requires overlap between the forward and reverse reads to create a full sequence of the target region (16S rRNA V4). This is not possible with the 150 bp reads generated by the iSeq100. Therefore, we can only process the forward read (150 bp). Forward reads are typically higher quality than reverse reads (as you’ll likely see in the read quality profiles below). Although a 150 bp sequence provides less taxonomic resolution than the full 250-350 bp V4 sequence, this is still sufficient to assign taxonomy to our sequences.

Examining read quality

We’ll start by visualizing the quality profiles of the forward reads:

plotQualityProfile(fnFs[1:2])

In gray-scale is a heat map of the frequency of each quality score at each base position. The mean quality score at each position is shown by the green line, and the quartiles of the quality score distribution by the orange lines. The red line shows the scaled proportion of reads that extend to at least that position (this is more useful for other sequencing technologies, as Illumina reads are typically all the same length, hence the flat red line).

The forward reads are good quality. We generally advise trimming the last few nucleotides to avoid less well-controlled errors that can arise there. These quality profiles do not suggest that any additional trimming is needed. We will truncate the forward reads at position 240 (trimming the last 10 nucleotides).

Now we visualize the quality profile of the reverse reads:

plotQualityProfile(fnRs[1:2])

It’s common for Illumina sequencing to produce reverse reads that are of lower quality - especially at the end. This isn’t too worrisome, as DADA2 incorporates quality information into its error model which makes the algorithm robust to lower quality sequence, but trimming as the average qualities crash will improve the algorithm’s sensitivity to rare sequence variants. Based on these profiles, we will truncate the reverse reads at position 160 where the quality distribution crashes.

Considerations for your own data

Your reads must still overlap after truncation in order to merge them later! The tutorial is using 2x250 V4 sequence data, so the forward and reverse reads almost completely overlap and our trimming can be completely guided by the quality scores. If you are using a less-overlapping primer set, like V1-V2 or V3-V4, your truncLen must be large enough to maintain 20 + biological.length.variation nucleotides of overlap between them

Filtering and trimming your data

First, we’ll assign new file names for the filtered .fastq.gz files we’re about to create.

filtFs <- file.path(path, paste0(sample.names, "_F_filt.fastq.gz"))
filtRs <- file.path(path, paste0(sample.names, "_R_filt.fastq.gz"))
names(filtFs) <- sample.names
names(filtRs) <- sample.names

To trim our data, we’ll use standard filtering parameters:

  • truncLen=c(200,200) : truncLen determines the cut-off length (in base pairs) for the forward and reverse reads.

  • maxN=0: DADA2 requires reads that have no Ns. This discards any read containing an ambiguous base.

  • rm.phix=TRUE: PhiX is a small phage originally isolated from E. coli and it’s DNA is commonly spiked in to Illumina sequencing libraries as a control. This parameter removes PhiX control reads.

  • maxEE=2: The maxEE parameter sets the maximum number of “expected errors” allowed in a read, which is a better filter than simply averaging quality scores. This discards any read with more than two expected errors.

  • truncQ=2: This truncates a read at the first base with a quality score ≤ 2.

  • multithread: This should be set to FALSE for Windows Operating Systems, or to TRUE for others.

  • compress=TRUE: This parameter saves filtered FASTQ files in a compressed (.gz) format.

out <- filterAndTrim(fnFs, filtFs, fnRs, filtRs, truncLen= c(200,200),
                     maxN=0, maxEE=c(2,2), truncQ=2, rm.phix=TRUE,
                     compress=TRUE, multithread=TRUE) #on Windows, set multithread=FALSE

head(out)
Considerations for your own data

The standard filtering parameters are starting points, not set in stone. If you want to speed up downstream computation, consider tightening maxEE. If too few reads are passing the filter, consider relaxing maxEE, perhaps especially on the reverse reads (eg. maxEE=c(2,5)), and reducing the truncLen to remove low quality tails. Remember though, when choosing truncLen for paired-end reads you must maintain overlap after truncation in order to merge them later.

For ITS sequencing, it is usually undesirable to truncate reads to a fixed length due to the large length variation at that locus. That is OK, just leave out truncLen. See the DADA2 ITS workflow for more information.

Adjustments for iSeq100 (2 x 150 bp) sequences 
out <- filterAndTrim(fnFs, filtFs, truncLen= 0,
                     maxN=0, maxEE=2, truncQ=2, rm.phix=TRUE,
                    compress=TRUE, multithread=TRUE) #on Windows, set multithread=FALSE (only needed for filterAndTrim)

head(out)

Denoising

DADA2 attempts to provide the most accurate possible reconstruction of the exact amplicon sequence variants (ASVs) truly present in a sample from the noisy amplicon sequencing reads this process is called denoising. Achieving high accuracy in DADA2 requires both high sensitivity (i.e. reporting as many real ASVs as possible) and specificity (i.e. not reporting out spurious amplicon errors).

Denoising consists of two parts:

  • Classifying reads as error-free, or not.

  • Mapping error-containing reads to the appropriate error-free ASV.

Learning the error rates

Every amplicon dataset has a different set of error rates. The learnErrors function estimates the sequencing error rate from your dataset to try and distinguish sequencing errors from true sequence variants (i.e., ASVs).

#learn errors
errF <- learnErrors(filtFs, multithread=TRUE)
errR <- learnErrors(filtRs, multithread=TRUE)

It is always worthwhile (as a sanity check, if nothing else) to visualize the estimated error rates.

plotErrors(errF, nominalQ=TRUE)

The error rates for each possible transition (A→C, A→G, …) are shown. Points are the observed error rates for each consensus quality score. The black line shows the estimated error rates after convergence of the machine-learning algorithm. The red line shows the error rates expected under the nominal definition of the Q-score. The estimated error rates (black line) should be a good fit to the observed rates (points), and the error rates should drop with increased quality.

Inferring sequence variants

#infer real sequence variants (denoised by taking the error rate into account)
dadaFs <- dada(filtFs, err=errF, multithread=TRUE)
dadaRs <- dada(filtRs, err=errR, multithread=TRUE)

#show the results for the first sample's forward and reverse reads
dadaFs[[1]]
dadaRs[[1]]

Constructing an ASV table

Merging paired reads

This step merges the forward and reverse reads to together obtain the full sequence, based on overlapping regions. By default, this function searches for 12 basepairs that match exactly - this condition can be adjusted using the minOverlap parameter.

#merge paired reads
mergers <- mergePairs(dadaFs, filtFs, dadaRs, filtRs, verbose=TRUE)

#inspect the merger data.frame from the first sample
head(mergers[[1]])
Considerations for your own data

Most of your reads should successfully merge. If that is not the case upstream parameters may need to be revisited: Did you trim away the overlap between your reads?

Adjustments for iSeq100 (2 x 150 bp) sequences 
# Merge dadaFs and filtFs
mergers <- mergePairs(dadaFs, filtFs, verbose=TRUE)
head(mergers)
Adjustments for ITS sequencing

For ITS sequences, you should increase the minimum overlap required between the forward and reverse reads, as ITS regions are more variable in length.

#merge paired reads
mergers <- mergePairs(dadaFs, filtFs, dadaRs, filtRs, minOverlap=20, maxMismatch=0, verbose=TRUE)
head(mergers)

Creating the ASV table

We can now construct an ASV table. The sequence table is a matrix with rows corresponding to (and named by) the samples, and columns corresponding to (and named by) the sequence variants.

This step filters out reads with lengths much smaller or larger than our target read length (~250-350 bp). The first step counts the occurrence of different read lengths in a table format. The second step allows you to trim sequence reads that are much shorter or larger than the read length with the highest counts.

#construct ASV sequence table
seqtab <- makeSequenceTable(mergers)
dim(seqtab)

#inspect distribution of sequence lengths
table(nchar(getSequences(seqtab))
      
#filter out reads larger or smaller than our target read length
seqtab2 <- seqtab[,nchar(colnames(seqtab)) %in% 289:296] 
table(nchar(getSequences(seqtab2)))
Considerations for your own data

Sequences that are much longer or shorter than expected may be the result of non-specific priming. You can remove non-target-length sequences from your sequence table (eg. seqtab2 <- seqtab[,nchar(colnames(seqtab)) %in% 250:256]). This is analogous to “cutting a band” out of a gel to get amplicons of the targeted length.

Adjustments for ITS sequencing

For ITS sequences, you should increase the allowed range of sequence lengths due to variability.

#merge paired reads
seqtab2 <- seqtab[,nchar(colnames(seqtab)) %in% 200:500]

Removing chimeras

Chimeras are not true sequence variants, but rather an artifact of the amplification process. Chimeras are ‘false’ DNA sequences formed by two or more biological sequences incorrectly joined together. Kind of like the mythological creature…

This often occurs during PCR reactions using mixed templates (e.g., environmental samples). Incomplete extensions during PCR allow subsequent PCR cycles to use a partially extended strand to bind to the template of a different, but similar, sequence. This partially extended strand then acts as a primer to extend and form a chimeric sequence. Once created, the chimeric sequence is then further amplified in subsequent cycles. The end result is a PCR artifact that does not represent a sequence that exists in nature.

Chimeric sequences can be identified if they can be exactly reconstructed by combining a left-segment and a right-segment from two more abundant “parent” sequences.

#remove chimeras
seqtab.nochim <- removeBimeraDenovo(seqtab2, method="consensus", multithread=TRUE, verbose=TRUE)
dim(seqtab.nochim)

#calculate the percentage of sequences that are non-chimeric
sum(seqtab.nochim)/sum(seqtab2)
Considerations for your own data

The frequency of chimeric sequences varies substantially from dataset to dataset, and depends on on factors including experimental procedures and sample complexity.

Most of your reads should remain after chimera removal (it is not uncommon for a majority of sequence variants to be removed though). If most of your reads were removed as chimeric, upstream processing may need to be revisited.

In most cases, this is caused by primer sequences with ambiguous nucleotides that were not removed prior to beginning the DADA2 pipeline. If you see over 25% of your sequencing reads being flagged as chimeric, trim the primers from your sequencing reads and restart the workflow.

Checkpoint: tracking reads through the pipeline

As a final check of our progress, we’ll look at the number of reads that made it through each step in the pipeline:

getN <- function(x) sum(getUniques(x))
track <- cbind(out, sapply(dadaFs, getN), sapply(dadaRs, getN), sapply(mergers, getN), rowSums(seqtab.nochim))
# If processing a single sample, remove the sapply calls: e.g. replace sapply(dadaFs, getN) with getN(dadaFs)
colnames(track) <- c("input", "filtered", "denoisedF", "denoisedR", "merged", "nonchim")
rownames(track) <- sample.names
head(track)
Considerations for your own data

This is a great place to do a last sanity check. Outside of filtering, there should no step in which a majority of reads are lost. If a majority of reads failed to merge, you may need to revisit the truncLen parameter used in the filtering step and make sure that the truncated reads span your amplicon. If a majority of reads were removed as chimeric, you may need to revisit the removal of primers, as the ambiguous nucleotides in unremoved primers interfere with chimera identification.

Assigning taxonomy

#assign taxonomy
taxa <- assignTaxonomy(seqtab.nochim, "silva_nr99_v138.2_toGenus_trainset.fa.gz", multithread=TRUE) 

head(taxa)

head(taxa)
Considerations for your own data

If your reads do not seem to be appropriately assigned, for example lots of your bacterial 16S sequences are being assigned as Eukaryota NA NA NA NA NA, your reads may be in the opposite orientation as the reference database. Tell DADA2 to try the reverse-complement orientation with the argument tryRC=TRUE and see if this fixes the assignments.

Saving your data

From our ‘raw’ microbiome sequencing data, we have produced the following end products:

  • An amplicon sequence variant (ASV) count table (seqtab.nochim) which records the numbers of times each exact amplicon sequence variant was observed in each sample.

  • A taxonomy table (taxa) which records the taxonomic assignments for each ASV.

The most important thing to do at this stage is to save and export our data so we can analyze it later. Today we’ll export these tables to .txt or .csv files.

#make a copy of your final ASV table
asv_count.data <- seqtab.nochim

#replace the column names with ASV numbers
ncol(asv_count.data)
final.asv.names <- paste("ASV",sep = "",rep(1:ncol(asv_count.data)))
colnames(asv_count.data) <- final.asv.names

#export your ASV table to a file
write.table(asv_count.data, file="asv_count_table.txt")

# Export your ASV names (i.e., your taxonomy file) to a file
taxa.data <- cbind(final.asv.names,taxa)
write.table(taxa.data, file = "taxonomy_table.txt")
